# Checkout 확인 및 계좌 미설정 처리

2026-10-09 로컬 HEAD: `602e84973eeb694fa6d12dc9dca95779345a9a5d`. 작업 전 변경은 사용자 소유의 미추적 이미지·엑셀 파일 3개이며 보존했다.

## 실제 서버에서 확인한 범위

공개 GET `/api/modules/sirsoft-ecommerce/settings/payment` 요청이 성공했다. 활성 결제수단은 `dbank` 하나다. `bank_accounts`는 1건이나 `is_active=false`, 계좌번호·예금주가 비어 있다. 실제 활성 계좌는 0개다. 임의 계좌나 상품·주문 데이터를 생성하지 않았다.

현재 템플릿은 계좌 카드 반복을 `is_active`로 필터링하면서 라벨은 항상 표시하므로, 이 API 응답에서는 “입금할 계좌 선택” 아래가 비게 된다. 설정 오류와 화면의 빈 상태 안내 누락을 구분한다. 관리자는 쇼핑몰 주문/결제 설정에서 실제 입금 계좌번호·예금주를 등록하고 계좌 사용을 활성화해야 한다.

## 수정

`checkout.json`의 `activeDbankAccounts`로 활성 계좌 목록을 공유한다. 계좌가 없으면 라벨 대신 관리자 설정 필요 안내를 표시한다. 무통장입금 선택 시 선택 계좌의 은행코드·계좌번호·예금주가 활성 목록과 일치하지 않으면 결제 버튼을 비활성화한다. 다른 결제수단의 진행 조건은 유지한다.

기존 `CreateOrderRequest`는 dbank의 은행코드·계좌번호·예금주 및 입금자명을 필수로 검증한다. 서버 요청 검증을 제거하거나 변경하지 않았다. 빈 계좌 상태를 UI에서 먼저 차단한다. 서버 API의 우회 요청 차단 범위를 새로 강화한 작업은 아니다.

## 화면·검증 한계

브라우저 연결 시 선택 실패와 사용 가능한 브라우저 목록 없음이 확인됐다. 따라서 실제 `/checkout` DOM, PC 1440px/모바일 390px, 스크롤, Console·Network, 전후 화면 및 필수값 오류 표시를 검증하지 못했다. 인증된 checkout 응답을 별도 수단으로 가져오거나 주문 생성 API를 호출하지 않았다.

로컬 summary는 `sticky top-4`이며 portable에서는 sticky 클래스를 해제한다. 버튼 반복이 실제 DOM 중복인지 전체 페이지 캡처 과정의 sticky 반복인지 단정할 수 없어 배치는 변경하지 않았다. 확인하려면 해당 장바구니 주문서가 열린 브라우저를 연결하고, 일반 화면 스크롤 중 버튼 개수·좌표와 전체 페이지 캡처를 비교해야 한다.

테스트는 로컬 G7 렌더러에서 실제 computed 표현식과 계좌 안내·결제 버튼, 주문자/배송지 필드 노드를 사용한다. 계좌 없음·비활성·미선택·정상 선택·삭제된 선택·다른 결제수단을 검사하고 주문자명/수령인명 필수 오류와 한글 입력을 확인한다. 전체 PC·모바일 레이아웃 검증이나 실제 서버 오류 응답 검증을 대신하지 않는다. 테스트 계좌는 로컬 fixture만 존재한다.

```sh
cd templates/_bundled/yutiv-stillform
npm run test:run -- __tests__/layouts/stillform.test.tsx __tests__/layouts/checkoutBank.test.tsx --maxWorkers=1 --pool=forks
npm run build
npm run check:static
```

서버 반영은 수행하지 않았다. 사용자 배포 시 기존 템플릿 업데이트 절차로 layouts/lang/dist를 반영하고 캐시를 갱신한 후, 실제 계좌 설정과 주문서 화면을 다시 확인한다. 주문이나 결제는 검증 목적으로 생성하지 않는다.
