# 상품 목록 중심 업무 0.5.0

상품관리 첫 화면은 재고 유무와 관계없는 실제 상품 목록이다. 내부 업무 탭은 없고, 우측 `신규상품입고`·`QR출력`, 행의 `추가 입고`·`상세·관리`로 시작한다. 상세/입고/QR에서 목록으로 돌아갈 때 검색·분류·날짜·재고·상태·정렬·표시 수·페이지를 복원한다. 필터에 가려진 입고 상품은 완료 알림에서 상세 또는 조건 해제로 접근한다.

## 목록과 옵션

이름/코드, 라이브 업체 전용 분류(기존 상품 미분류), 등록일/입고일, 판매 가능 재고 유무, 특정 상태 물품 존재를 DB에서 조회한다. 날짜는 업체 시간대의 시작일 00:00 이상~종료 다음날 00:00 미만이다. 입고일 검색은 배치 헤더와 헤더 없는 과거 입고 이동을 모두 포함하며 중복 상품을 만들지 않는다. 기본 최신순/오래된순/상품명순에 ID를 더해 안정 정렬하고 20/50/100개 페이지와 정확한 전체 상품 수를 제공한다. 상태 조건은 상품 선택 조건이며 행의 상태별 수량은 해당 상품 전체다. 옵션/판매가 범위/8개 재고 상태는 페이지 SQL의 상관 집계로 읽으며 상품별 추가 조회를 하지 않는다.

옵션은 기본 1개 또는 최대 4종류×각20값, 조합50개다. 조합 재생성은 같은 종류·값 조합의 입력을 보존하고 입력이 있는 조합을 제거할 때 확인한다. 기존 옵션 ID·주문·QR은 삭제하지 않는다. 기존 옵션은 입고로 판매가를 바꾸지 않으며 상세에서 별도로 저장한다. 과거 옵션50개 초과 상품도 선택한 양수 수량의 옵션만 제출하여 추가 입고할 수 있다(한 배치 최대50옵션/200물품). 기본 옵션의 가격도 직접 입력한다.

가격 모드 전환 자체는 입력을 바꾸지 않는다. `전체 옵션에 적용`만 공통값을 적용하며 다른 값 덮어쓰기를 확인한다. 할인은 원화 금액이며 판매가격 이하이다. 원가·판매가·수량 계산은 정수이고 클라이언트 합계는 BigInt, 서버는 64비트 정수다.

## 입고단가와 장부 기준

신규 HTTP 입고는 물품당 `unit_cost` 정수 KRW 0~1,000,000,000원이 필수다. 누락·음수·소수는 거절하고 명시한 0원은 허용한다. `live_receipt_items`는 업체/배치/상품/옵션/단가/수량/매입금액/통화를 확정하고 이번 물품만 `receipt_item_id`로 연결한다. 다른 배치 단가로 기존 물품 원가를 덮어쓰지 않는다. 수정 엔드포인트는 제공하지 않는다. 기존 저수준 서비스 호출 및 이전 물품은 단가 null=미등록이고 0원으로 추정하지 않는다. 이전 단건 입고 HTTP도 새 요청부터 같은 배치·단가 경로를 사용한다. 이미 확정된 이전 요청의 같은 키 재시도는 기존 해시·결과를 유지한다.

새 기준 `operational-events-3-purchases`는 **입고 확정일의 단가×수량**을 기간 매입금액으로 집계하고 단가 등록/미등록 수량과 불완전 여부를 표시한다. 원래 입고 이동이 있는 과거 미등록 물품도 미등록 수량에 포함한다. 매출원가·재고평가·FIFO·세금·이익은 계산하지 않는다. 기존 주문 발생·입금 변동·취소/반품·환불·재고 전이 기준은 그대로다. 저장 보고서는 새 매입 상세를 추가 보존한다. 0.4.0 저장 결과/상세/기준 버전은 변경하거나 재계산하지 않으며 재생성은 새 UUID다.

입고 권한자는 이번 단가를 입력한다. 과거 단가/입고 완료 매입 합계는 기존 settlement 권한만 조회하며, 재무 장부도 기존 권한을 유지한다. 판매 직원의 catalog, 창고의 inventory/labels, 재무의 settlement 권한을 확대하지 않았다. 고객·공개 상품·QR 라벨·일반 출력 이력에 단가를 포함하지 않는다.

## QR 출력과 이력

현재 페이지에서 선택한 상품(무선택은 검색 시작), 최근 입고 배치, 이름/코드·상태 검색, 개별 UUID, 저장된 출력 요청 및 이전 버전 감사 기록에서 실제 물품을 찾는다. 물품 목록은50개 페이지로 전체 대상 수를 알리고 페이지별로 나누어 선택·출력한다. 검색 전체나 다른 페이지를 조용히 선택/절단하지 않는다. 라벨 설정은 접혀 있고 기본50×30mm/물품당1장이다. 물품당1~10장, 한 요청 총200장 이내이며 초과는 서버/화면에서 거절한다.

미리보기는 기록하지 않는다. 미리보기의 인쇄 요청 버튼이 서버에 UUID·업체·작업자·시각·크기·매수·총장수·입고 참조·표시명·원본 요청 연결을 저장한 다음 인쇄창을 연다. 실패하면 열지 않는다. 같은 키/같은 입력은 같은 결과, 바뀐 입력은409이고 의도적 재출력은 새 키와 원본 ID다. 개별 UUID 연결 테이블로 최초 **기록된 요청**을 찾는다. 실제 프린터 성공이나 과거 최초 발행 시각을 추정하지 않는다. 0.4.0 감사 이력 재출력은 당시 UUID 목록 및 감사 ID를 새 요청에 연결한다. 과거 기록은 변경하지 않는다. 재출력 표시명은 현재 상품/옵션명으로 새 요청에 보존하며 UUID는 같다.

## 스키마와 공식 적용/복구

`2026_10_21_000007_create_live_product_workspace.php`: live_categories, live_receipt_items, live_label_requests, live_label_request_units 추가. 상품 category_id, 옵션 attributes JSON, 개별 물품 receipt_item_id 및 조회 인덱스를 추가한다. 기존 업무 행을 UPDATE/DELETE하지 않는다. 분류·단가·출력 요청이 있으면 down을 거절한다. 운영 중 단순 버전 후퇴로 새 기록을 잃지 않도록 전진 복구한다.

배포 대상은 이 플러그인의 소스·뷰·CSS/JS·언어·migration·manifest 5종·components.json·dist·문서다. 코어 변경/새 의존성 없음. 공개 라우트/서비스 변경에 대해 번들 확장 의존 manifest를 스캔하며 소비 확장이 없어 타 확장 최소 버전 변경 없음.

배포 담당자가 백업 및 업무 중지 후 공식 절차를 수행한다(이번 작업에서는 실행하지 않음):

```text
php artisan plugin:update yutiv-live_commerce --source=bundled --force
php artisan plugin:vendor-verify yutiv-live_commerce
php artisan route:cache
```

프런트 수정 시 공식 `plugin:build yutiv-live_commerce --production` 후 생성된 dist/components.json을 함께 전달한다. 복구는 코드·DB·파일 백업을 같은 시점으로 함께 복원하는 사전 검증된 절차 또는 수정 버전의 전진 업데이트다. 새 비용/출력 기록을 남긴 DB에 과거 코드만 덮어쓰거나 migration down을 강제하지 않는다.

## 상태 정책

기존 `lost`는 화면의 ‘망실’이다. 별도 ‘분실’ enum/전이/회계 정책은 존재하지 않아 새 상태나 동의어를 만들지 않았다. 예약은 정상 가용 재고에서 제외하고 A/S·반품·출고·불량·폐기 원장 정책을 그대로 사용한다. 분실을 별도 구분하려면 상태 의미·전이·기초/기말 영향의 업무 결정이 먼저 필요하다.
