# 0.7.0 방송관리 통합

기준 branch `main`, 시작 HEAD `09389ffbea5691593dd536ecff7c46ec1352fb63`, 플러그인 0.6.0. 시작 작업 트리는 깨끗했으며 수정은 이 플러그인 내부에 한정했다. commit·push·운영 접속·운영 DB 변경·배포 없음.

## 원인과 생성 흐름

기존 `LiveOfficeService::data`는 업체의 활성 쇼호스트 명부 전체를 가져왔고 `seller/office.blade.php`의 hosts 분기가 모든 인원을 `host_shares[ID]` 입력으로 렌더링했다. 수정 시 저장된 지분이 없는 인원도 0으로 표시·제출했다. 따라서 Jessi는 실제 선택 여부와 관계없이 폼에 나타났으며, 한 명 자동 선택을 명시적으로 처리한 코드가 원인은 아니었다. 기존 저장 JSON을 추정해서 지우거나 일괄 변환하지 않았다.

이제 왼쪽 **방송관리** 안에 방송 목록·유튜브 채널·쇼호스트 탭이 있다. 방송판매 상품은 독립 메뉴에서 제거하고 방송 상세에 통합했다. 기존 판매 링크 관리와 코드·귀속 구조는 그대로다. 기존 채널·쇼호스트·방송상품 URL도 권한 검사 후 연결한다.

첫 화면은 검색/채널/시작 예정일/실제 지원 상태 필터와 방송 목록이다. ‘새 방송’에서 기본 정보를 입력하고, 필요한 쇼호스트만 선택해 저장한 뒤 상세에서 판매상품을 추가한다. 저장·취소·목록 복귀에 목록 검색/페이지 조건을 유지하며 방송상품 검색/페이지도 저장 후 유지한다.

방송명은 업체 시간대의 시작 예정일과 오전/오후로 실제 입력값을 만든다. 사용자가 이름을 수정하면 이후 날짜 변경이 덮어쓰지 않는다. ‘이름 자동 생성’으로 다시 연동할 수 있다. 판매시간은 기본적으로 방송 예정과 같으며 기존 별도 판매시간은 체크된 상태로 불러온다. 종료가 시작 이하인 값은 서버에서 거절한다.

현재 채널 스키마에는 name/url/active만 있으며 계좌·요율·방송시간 기본값은 없다. 채널 정보는 서버가 같은 업체의 선택지에 함께 넣어 즉시 표시한다. 새 비동기 요청이 없으므로 응답 순서 역전이 없고, 회차 영상 URL·직접 작성 이름·시간·요율을 덮어쓰지 않는다. 채널 주소를 회차 영상 URL로 복사하거나 외부 YouTube API를 호출하지 않는다.

## 참여자와 실제 계산

신규 방송은 등록된 쇼호스트가 한 명이어도 미선택이며 쇼호스트 수수료 0%다. 선택된 인원만 표시·제출하고 중복 선택을 막는다. 기존 수정은 저장된 host_shares와 요율을 그대로 읽는다. 비활성으로 전환된 기존 참여자도 임의 해제하지 않는다. 새로 추가하는 목록은 활성 인원이며 다른 업체 ID는 서버에서 거절한다.

한 명은 지급 지분 100%, 여러 명은 지분 합계 100%가 필요하다. 다수 참여자 추가 시 기존 지분을 유지하고 새 인원은 0%로 시작한다. 다수에서 삭제해도 남은 여러 사람의 지분은 자동 재분배하지 않는다. 한 명만 남으면 명시된 단독 진행 규칙에 따라 100%가 된다. ‘균등 배분’은 0.01% 정밀도로 나누고 나머지를 ID 오름차순에 배분한다. 준비 상태에도 지분 합계를 검증하므로 미완성 지분으로 판매 상태에 진입할 수 없다. 참여자 미정 준비/예정 방송은 수수료 0으로 저장할 수 있다.

기존 `IncentiveCalculator` 의미를 유지한다. 계산 대상은 주문 당시 할인 후 상품 단가×수량이며 배송비는 제외한다. 요율·지분은 정수 10000분율이다.

1. 채널 운영자 수수료 = 대상 금액×채널 요율, 원 미만 버림.
2. 쇼호스트 공동 재원 = 대상 금액×쇼호스트 수수료율, 원 미만 버림.
3. 공동 재원×각 지급 지분을 원 단위로 나누고, 남은 원은 기존 최대 잔여 방식(잔여 내림차순, 동률은 ID 오름차순)으로 배분.

예: 100,000원, 채널 3.33%, 쇼호스트 5.25%, 두 명 지분 33.33/66.67이면 채널 3,330원, 쇼호스트 1,750/3,500원, 총 8,580원이다. 지분은 전체 쇼호스트 수수료를 나누는 비율이며 매출에 추가되는 요율이 아니다. 화면 예상액은 같은 정수 계산을 쓴다. 실제 확정·지급·반품 조정 조건은 기존 인센티브 원장을 따른다.

상품별 기존 예외 요율도 유지하며 화면에서 확인/수정할 수 있다. 활성 예외와 새 참여자 구성이 충돌하면 저장을 거절한다. 주문 진입에도 계산 검증을 적용하므로 불완전한 기존 설정을 정상 주문으로 확정하지 않는다. 이미 생성된 주문의 가격·귀속·수수료 스냅샷과 지급 원장은 변경하지 않는다.

## 방송상품과 고객 노출

원본 상품을 카테고리·이름/코드·가용 재고로 검색하고 옵션별로 추가한다. 선택된 옵션의 순서/방송 노출/기존 예외 요율을 관리한다. 원본 가격 변경 권한은 확대하지 않는다. 방송 내 숨김은 상품 published/sellable, 옵션 active, 실제 재고를 변경하지 않는다. 같은 방송·옵션 중복 추가는 기존 행을 반환하며 다른 방송/옵션으로 기존 행을 옮길 수 없다.

DB 상태는 기존 draft/selling/closed 3개다. 화면의 예정/판매기간 종료는 selling의 판매시간으로 계산한 표시이며 외부 실제 방송 송출 여부를 추정하지 않는다. 고객 노출 우선순위는 다음과 같다.

1. 업체 및 판매 링크 유효성·해당 방송 귀속.
2. selling이며 판매 시작 ≤ 현재 UTC < 판매 종료.
3. 해당 방송상품 active.
4. 원본 상품 published/sellable 및 옵션 active.
5. 가용 재고 0이면 품절 표시·담기 버튼 비활성. 서버의 원래 재고 재확인은 계속 적용.

시간 입력/조회 기간은 업체 시간대로 해석해 UTC와 비교한다. 별도 판매시간이 있다면 방송 예정 전/후라도 그 판매시간이 기준이다. 동시 방송은 일반 고객 목록에서 방송명을 구분하고 방송별 링크에는 해당 상품만 나온다. 타 방송/업체 판매 코드를 조합하면 거절한다. 방송 종료 후 기존 예약·입금·출고·취소·반품 처리 규칙은 유지한다.

## 변경·배포·제한

추가: `LiveBroadcastWorkspace`, `LiveBroadcastController`, `LiveBroadcastRequest`, 방송 Blade/JS/CSS, 회귀 테스트·브라우저 시나리오·문서. 수정: 기존 MENU/LiveRoutes, CatalogRequest와 Catalog/OfficeService 연결, 고객 품절 표시·안정적 정렬, 운영 레이아웃의 화면 전용 밀도 조정. 공개 Golfif 메인 디자인은 수정하지 않았다. 공통 밀도 조정은 navigation을 가진 판매자 화면의 PC 화면에만 적용하며 인쇄 규격에는 적용하지 않는다.

기존 스키마의 방송·JSON 참여자·방송상품 active/position을 사용하므로 **신규 migration 없음**. 기존 라이브 주문·재고·관리 회계·인센티브 원장에 대한 데이터 변환 없음. 다른 번들 확장에 이 플러그인 소비 의존성이 없어 최소 버전 동기화 대상 없음. 플러그인 manifest/composer/package/package-lock/components 등록 정보와 배포 dist를 0.7.0으로 갱신한다.

배포 대상은 `plugins/_bundled/yutiv-live_commerce/` 전체다. 다음은 격리 복사본에서 실행한 공식 절차이며 운영에서는 실행하지 않았다.

```sh
php artisan plugin:build yutiv-live_commerce --production
php artisan plugin:update yutiv-live_commerce --source=bundled --force
php artisan route:cache
php artisan vendor:verify
```

배포 전 동일 시점 코드·DB·첨부·암호화 키를 백업한다. 복구는 해당 전체 백업 복원 또는 수정 버전 전진 업데이트를 사용한다. 신규 migration이 없어도 신규 방송/정책을 임의로 과거 상태로 되돌리지 않는다.

남은 범위: YouTube 외부 API/송출 상태 자동 감지, 채널별 계좌/요율 기본값 신설, 다수 참여자의 미완성 지분 임시 저장은 제공하지 않는다. 기존 DB의 0% 참여자 키를 실제 선택 의도로 추정해 정리하지 않는다. 검증은 합성 격리 환경 PHP 8.4.26 / MySQL 8.4.11이며 대상 PHP 8.3.6 / MySQL 8.0.46에서 직접 실행한 결과는 아니다.
