# 운영 장부 0.4.0 집계·보존·출력 기준

0.3.0 입고 배치/상품/옵션/QR 흐름을 유지한다. 이 기능은 업무 기록이며 정식 회계 마감·세무 장부가 아니다. 원가·세금·이익 계산은 제공하지 않는다.

## 기간 발생과 현재 분석

집계 기준 버전 `operational-events-2`. 업체 시간대의 시작일 00:00 포함, 종료일 다음날 00:00 제외. 주간은 월요일 시작, 월간은 달력 월이다. 최대 조회 기간 366일은 유지한다.

| 항목 | 기준 | 의미 |
| --- | --- | --- |
| 주문 발생액 | 주문 생성일 | 원본 수량 × 주문 당시 스냅샷 단가. 배송비 제외 |
| 입금 확인액 변동 | deposit 기록일 | 이번 누적 확인액 − ID 순서의 직전 deposit 누적 확인액. 이전 확인이 기간 밖이어도 반영. 음수 정정 가능 |
| 입금 검토 완료 | deposit_review 기록 | 추가 입금으로 합산하지 않음 |
| 취소·반품 | 각각의 이벤트 기록일 | 해당 기록 금액 및 수량, 서로 구분 |
| 환불 기록 | refund 기록일 | 수동 환불 기록. 은행 송금 검증/완료를 뜻하지 않음 |
| 판매 출고 | ship 이동 기록일 | 실제 물품 이동 건수 |
| 기초·기말 재고 | 경계 직전 이동 원장 | 물리적 보유량, 상품 금액 평가 아님 |
| 현재 미입금 | 조회 시점의 현재 상태 | max(0, 잔여 상품금액 + 배송비 − 누적 입금 확인액)의 주문별 합. 과거 기말 미입금 아님 |
| 현재 주문 상태 | 조회 시점의 현재 상태 | 기간과 무관한 해당 주문 조건의 결제/배송 상태별 건수 |
| 현재 잔여 상품금액 | 기간 생성 주문의 현재 paid 상태 | (원본 수량 − 누적 취소 − 누적 반품) × 스냅샷 단가. 환불을 다시 차감하지 않음 |

기간 순매출은 제공하지 않는다. 입금액을 회계상 매출로 단정하거나 주문액에서 입금·취소·반품·환불을 합쳐 차감하지 않는다. 현재 잔여 상품금액도 과거 마감 매출이 아니다. 채널/쇼호스트 귀속은 최신 정정으로 분석하며 같은 금액의 다른 분석이므로 합산하지 않는다. 공동 진행자는 참여 금액이며 진행자 간 합산하지 않는다.

상품 필터: 주문액·취소·반품·판매 출고·재고·현재 잔여 상품금액은 선택 상품의 항목만 대상으로 한다. 입금·환불·현재 미입금·현재 주문 상태는 해당 상품을 포함한 주문 전체 기준이다. 혼합 주문의 현금 기록을 상품에 임의 배분하지 않는다. 저장 이벤트 상세는 관련 주문의 참고 기록도 보존하며 `included_in_period_totals`로 집계 포함 여부를 구분한다.

## 누적 데이터와 조회 일관성

업체 전체 물품/주문/옵션/이벤트 수에 따른 기존 차단을 없애고 DB에서 조건 조회/집계한다. 금액·수량 합계는 페이지와 무관하게 조회 조건 전체다. 화면은 20개 옵션씩 표시한다.

기초 재고는 기간 안 이동만 읽어 추정하지 않는다. 해당 업체/상품/옵션의 전체 물품 이력을 DB window 함수로 검사한다. 첫 receive/from_state=null, 모든 이전 to_state와 다음 from_state, 최종 상태/위치와 현재 물품을 대조한다. 기초/기말은 경계 이전 보유 증감의 합이다. 원장 누락/전이 단절/최종 상태·위치 불일치가 하나라도 있으면 해당 옵션과 전체 재고 합계는 산출 불가로 표시한다. 후속 기간 이동도 현재 이력의 무결성 검증에 사용한다.

보유 상태는 available/reserved/returned/as/defective. shipped/lost/disposed는 비보유다. 기초 + 입고 + 출고(음수) + 반품 + 망실·폐기(음수) + 외부 A/S 증감 + 조정 = 기말. 예약/해제/위치 이동/내부 A/S는 증감 0. 출고품 A/S 접수는 외부 유입, 원래 shipped 상태로 반환하는 A/S 반출은 외부 유출이다.

조회/저장은 writer 연결의 한 REPEATABLE READ 트랜잭션에서 일반 SELECT로 읽는다. 업체 행 FOR UPDATE/공유 잠금을 요청하지 않는다. Laravel은 트랜잭션 안에서 read replica로 분리하지 않는다. 감사 기록은 보고서 트랜잭션이 끝난 뒤 쓴다. 새 보고서/상세의 INSERT는 새 보고서 행에만 쓰고 INSERT SELECT를 사용하지 않는다. 업체 FK의 공유 잠금이 업체 쓰기 mutex를 막지 않도록 보고서 테이블의 tenant_id는 앱의 업체 격리와 인덱스로 관리하며, 상세의 report_id FK만 적용한다.

PHP에 업체 전체 주문·물품·이동을 적재하지 않는다. 옵션/상세는 100행, 현재 귀속 분석은 250행 배치다. DB 원장 검사 작업량과 보존 용량은 이력에 비례하며 무한 규모/일정 응답시간을 보장하지 않는다.

상태 전이와 최종 상태/위치는 CAST AS BINARY로 비교하여 DB의 대소문자 무시 collation이 기존 PHP의 엄격한 비교를 완화하지 않게 한다. 입고 유형 및 보유 상태 판정도 같은 바이트 비교를 사용한다.

## 저장 보고서와 분할 출력

`POST /seller/reports`는 from/to/period/product_id 조건으로 전체 보고서를 생성한다. 저장 목록은 장부 화면 아래 10개씩 조회한다. `GET /seller/reports/{uuid}?part=N`으로 재조회·재출력한다. 기존 settlement 권한(owner/finance)과 업체 격리를 모든 경로에서 재확인한다. CSRF 및 기존 세션 보호를 유지한다. 타 업체 UUID는 404다.

`live_reports.result`에 업체명, 기간, 시간대, 기준 버전, 생성 시각, 생성자 ID/이름, 전체 집계와 생성 당시 현재 분석을 저장한다. `live_report_rows`에는 옵션별 재고/실적, 기간 주문 항목의 원본 스냅샷·현재 상태, 기간 이벤트와 입금 직전 누적 확인액/차액, 기간 이동을 저장한다. 계좌/배송 비밀값은 저장하지 않는다. 헤더/상세 SHA256을 재조회 때 확인한다. 저장 도중 실패하면 전부 롤백되어 부분 보고서를 공개하지 않는다.

저장 보고서는 원본 상품명·주문·반품을 재조회해 계산하지 않는다. 이후 원본 변경은 저장 결과/상세에 영향을 주지 않는다. 재생성은 별도 UUID 버전으로 추가되며 덮어쓰기/수정/삭제 경로는 없다. 생성 시각은 산출 시각이며 원본 데이터는 해당 트랜잭션의 MVCC 일관 읽기 시점이다.

화면 페이지를 바로 인쇄하지 않는다. ‘전체 보고서 저장·인쇄 준비’로 전체 조건을 저장한 뒤 최대 100행씩 분할 출력한다. 모든 분할에 같은 전체 합계·보고서 UUID·분할 번호를 표시한다. 전체 합계는 분할 간 다시 합산하지 않는다. 각 상세 순번은 1부터 전체 행 수까지 연속이며 분할 전체를 출력하면 모든 상세가 포함된다. 분할 번호 직접 이동/이전/다음으로 큰 보고서도 마지막 분할까지 조회한다. 브라우저 PDF/인쇄 요청은 실물 인쇄 완료 증명이 아니다.

## Migration 및 배포 준비

0.2.0에서 최종 0.4.0으로는 000005(입고 헤더)와 000006(보고서 두 테이블 및 복합 인덱스)이 추가 실행된다. 0.3.0에서는 000006만 추가된다. 기존 상품/옵션/주문/물품/QR/원장 데이터를 갱신·삭제·추정 이관하지 않는다. 보고서가 존재하면 000006 down()은 거절한다. 데이터가 있는 운영에서 후진 rollback 대신 백업과 전진 복구를 사용한다.

배포 대상은 플러그인 전체 PHP·뷰·언어·migration·manifest·components.json·dist 및 문서다. 코어 변경 없음. 기존 백업/업무 중지/자동 실행 점검 절차는 [입고 운영 지침](RECEIPTS_LEDGER.md)을 따른다. 배포 담당자가 공식 `plugin:update yutiv-live_commerce --source=bundled --force`, `plugin:vendor-verify`, `route:cache`를 수행한다. 이 작업에서는 commit/push/운영 접속/배포하지 않는다.
